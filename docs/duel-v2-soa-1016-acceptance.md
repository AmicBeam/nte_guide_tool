# 1016：专用 SoA、批量规则与 Mctx 对照验收协议

本文件规定本次架构改造的验收方法，不是单次实测报告。实测配置、日志、失败样本、计时、完整对局和结论只保存到 `artifacts/rl-evals/<run-id>/`。规则仍以[完整手册](everness-item-chain-card-design.md)为准；训练及模型质量另按[训练手册](duel-v2-public-training.md)和[完整报告规范](duel-v2-full-training-report-spec.md)验收。

## 本次范围

目标是将七队搜索热路径从通用对象图迁到逐字段的领域 SoA，并使规则直接批量读写这些列。不能把原生编译、字典节点数组化、SoA 装箱副本或算术原语完成写成完整规则迁移完成。现有原生数组后端保留为独立对照，不能悄悄作为新后端的逐步回退。

覆盖17名公开角色和七队：创生、覆纹、小吱、真红、浊燃、倾陷、灵可。海月虽未出现在这七套当前构筑中，仍属于公开规则覆盖；鬼郎丸等召唤物须保存独立实体身份。四名测试角色及教学机制不纳入这次公开七队资格，但遇到其状态必须明确拒绝，不能删字段后继续。

搜索配置沿用用户本轮约定：每个独立根 Gumbel32、根候选 cap16、固定观察者 network-WDL、horizon0、冻结策略对手。移除三步规则教师；真红指导仅从当前合法可见观察及完整候选计算有界根 logit 位移，不模拟、不改变真实奖励、不在搜索完成后覆盖动作。完整合法候选不以 cap16 截断；cap16 仅限制根搜索选出的候选。

不启动优化器、修改权重、发布模型或部署服务。Windows 离线时执行本机实现与对拍，设备计时、显存、CUDA捕获及完整设备终局记为待验证。

## 第一步：逐字段 SoA 与直接规则计算

### 状态布局的完成条件

| 对象 | 必须保存的语义 |
| --- | --- |
| 对局 | phase、实际行动方、先手、全局回合、胜者／原因、版本、实体／卡实例分配器、完整随机状态 |
| 玩家 | hp／max_hp／shield／ap、回合计数、前排／最近来源、瞬发与普通出击、终结次数、公开累计事实及临时效果 |
| 异能者／召唤物 | 独立entity_id、模板与编队顺序、生命／护盾／个人资源、武备、永久成长、倾陷、个人计次、复制异能、条件与到期状态 |
| 实体牌与区域 | 实体身份、原牌／衍生／生成／复制归属、金谷标注、视为牌、手牌／牌库／弃牌／移除区的精确顺序 |
| 修正与区域效果 | 层、运算、条件、来源、作用对象、到期方与时点、清除／消费规则、持续伤害的类型与层数 |
| 选择与操作续步 | 所有公开角色选择种类、候选实体引用及顺序、正在结算的牌、出击暂停、占卜整理与延后操作 |
| 事件与重放 | 搜索所需公开事实及物理动作记录。省略展示数据须单独证明不会影响规则、编码、采样或回放；不能默认删除事件 |

数值字段采用明确的整数／布尔／浮点列；不同实体之间使用索引／身份引用。变长表有容量、计数与有效掩码。未知字段、类型、条件、卡效、容量不足和整数溢出均拒绝；缺失、null、false和0不能混同。320位采样种子与规则中的63位随机状态不截成31位，不更换正式随机过程。

实体和临时操作的共享引用必须保留：选择候选或结算中卡牌引用同一个实体，不能复制成第二张牌。观察和公开录像不能泄漏牌库顺序、对方暗牌、私有检视及种子。

### 批量执行的完成条件

1. 初始化后的搜索状态以SoA为权威；推进、合法动作、观察编码和隐藏世界采样直接操作设备列。不能每一步先还原字典或通用图，再把结果重新装箱。
2. 所有真实行采用活动掩码；错误行回滚或永久失效，非活动尾槽不产生效果。多步卡效、响应、同时伤害、倒地连锁、自然到期和选择续步保持正式顺序。
3. 树中分支具有独立可写状态；父根、其他采样世界及未选择的分支不可被修改。无CPU规则回调、逐根主机控制、隐式同步或未登记的回退。
4. 完整卡效及角色事件须有实际执行器；覆盖表里写了名称、能导入或能生成源码不等于实现完成。只接算术原语时，完整规则和完整搜索资格仍为false。
5. 新增终局只发一次真实WDL，连续行动不按深度翻转价值符号；超时、容量错误或决策保护上限不转成输／平。

### 本机离线核验

- 每个领域字段做真实状态往返检查，比较完整状态、类型、实体身份、共享引用、区域顺序和RNG；覆盖两侧视角、缺字段、null、负金谷、已用次数、倒地、召唤与选择中断。
- 批量规则由新内核先执行，正式引擎仅作事后oracle。比较完整状态、完整有序合法动作、观察与候选编码字节；对无损字段单列限制，不能只比hp后宣称整局一致。
- 七队至少14个明确轮换先手的自然对局作规则链路检查，另有机制夹具覆盖未自然触发的卡效。自然局数量不代替逐卡／事件覆盖；本机规则局不算GPU吞吐或模型互搏胜率。
- 验证混合阶段／行动方／结束状态／错误行／非活动尾槽、越界拒绝和输入不变性。Torch CPU数值对拍与实际CUDA捕获用例分别计数，skip不能算通过。
- 若字段装箱或部分阶段仍未支持，列出具体字段／机制及失败样本，完整SoA迁移保持未完成。

## 第二步：Windows 实机性能与自然终局

### 先正确性，后计时

新源码和实际设备先完成相同规则／编码／随机／采样对拍，再进入设备内闭环。保存真实独立的根，而非把同一根复制8份；至少覆盖七队、双方行动和选择阶段。CPU只在批次外导入／导出、编译和事后重放。

8路每根32搜索先验证：固定模型、构筑、输入、候选、随机流和价值视角，分别比较旧原生后端与SoA后端的采样世界、假想推进、Gumbel分配、访问次数、完成Q、完整pi和最终原始动作。改变浮点归约顺序时事前声明容差；身份、合法顺序、整数与随机语义要求精确一致。

### 计时口径

| 指标 | 记录方式 |
| --- | --- |
| 冷启动 | 导入、模型加载、源码生成／编译、设备分配、捕获，单独记录 |
| 纯搜索 | 同批真实根从可搜索到完整32搜索完成；GPU事件时间与墙钟分别记录 |
| 真红先验 | 单独记录调用行数与设备耗时，说明是否已包含在纯搜索中 |
| 物理一步 | 编码、采样、完整搜索、先验及实际动作提交的整批端到端时间 |
| 分环节 | 状态复制、采样、合法动作／编码、规则推进、推理、树调度／回传；嵌套区间不直接相加 |
| 并发 | 总局数、驻留根、同时活跃搜索根峰值、规则工作槽、推理微批分别记录 |
| 资源 | 实际显存allocated／reserved／设备峰值、工作区与轨迹容量、CPU/GPU传输和同步次数、后台负载 |

先预热至少两批，再对固定输入重复至少三批，保存每批原始时间并报告中位数及样本量；足够批次后才给有意义的p95。重复同批不增加独立局面或胜率样本。计时失败、未满32、截断候选或错误行不得进入合格吞吐。

### 自然对局与扩容

8路完整一步通过后先跑8路真实完整局至自然结束，测每局决策数、全局回合、真实终局耗时及完成局／小时。根据实测内存、延迟和吞吐，按8→32→128→400→1600逐级验证；每级仍有完整搜索、自然终局、GPU原始动作重放及信息集哈希检查。工作区tile不等于并发根，前级失败不直接跳到更高并发。

每批预先声明截止和保护上限，失败保存输入与错误，不改CPU规则补完。完整自然局之前仅报告局部计时，不外推“已能每小时训练多少局”。吞吐估计必须包含长尾与实际活跃行变化；预测49局或完整矩阵所需时长时给出实测局速、样本数及不确定范围。

首轮49格仅用于七队对阵的功能／性能覆盖：先手为行、后手为列，每格真实一局，含对角线内战。不是模型质量验收；完整质量矩阵仍按预声明样本、独立种子及完整报告规范执行。

## 第三步：官方 Mctx 的结果与性能对照

目的有两个：校验自维护搜索实现的算法语义，以及判断继续维护Torch搜索还是迁入JAX是否值得。直接换库不作为SoA或规则性能的替代验收。

### A. 可比数值树的算法对照

用官方 `mctx.gumbel_muzero_policy`，与当前搜索比较32模拟／cap16的根分配、sequential halving、completed-Q、改进策略目标及最终动作资格。记录实际算法参数、根候选顺序、值尺度、无效动作掩码、最大深度与单合法动作的预算规则。

完全一致比较须输入相同Gumbel噪声及同一数值转移树；不能把JAX与Torch设为相同整数seed就认定随机数相同。若接口不允许控制相同噪声，报告限制，改做确定性／统计对照并解释差异。当前方连续行动和换边时明确转换固定观察者价值，不能照搬默认双方交替符号。

离线录制的完整数值树用于检查搜索算法，不能等同于真实规则性能或信息集搜索。只记录原实现访问过的分支而缺少Mctx可能访问的分支时，不得以默认零值补齐；应拒绝该比较或补齐固定测试树。

### B. 同一真实规则与推理的设备对照

只有SoA规则及批量推理能在Mctx的JAX编译调用内实际执行后，才比较真实端到端性能。两者保持同一冻结模型、完整合法候选、信息集采样协议、观察者、实际模拟数和输出定义。若需自定义调用或跨框架桥接，记录同步／传输及编译成本；不能用预录查表的Mctx时间与真实规则搜索时间比较提速。

普通Mctx状态树不自动实现本项目隐藏信息搜索。固定世界、根采样、重新确定化、信息集键和跨世界复用必须明确一致；适配不完整时仅报告数值树算法对照，真实规则对照保持未完成。

### C. 是否换库的决定

- 先看步骤A是否揭示真实语义差异，修复或解释后再比较性能。
- 步骤B以至少三轮匹配任务的预热后墙钟中位数、显存及完整自然局吞吐比较；冷启动、跨框架开销另列。
- 若规则仍占主要耗时，继续优化规则列和内核；若搜索调度／树运算占比明显且Mctx实测有收益，再提出迁移结论。
- 维护收益与性能收益分别写明。不提前承诺换库更快，不以论文或官方示例替代本项目测量。
